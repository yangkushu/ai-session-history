# 下一版设计草案：一个历史引擎，多个使用入口

本文落实[下一版本规划](next-version-plan.md)的第一步：先确定项目范围、会话模型和交接流程，再决定代码怎么摆放。不启动验证或实现，目录和接口名称都是建议。

## 1. 代码结构

```text
src/
  core/           会话模型、项目范围、查询和交接
    readers/      每个来源一个入口，封装发现与格式读取
  cli/            参数、命令执行、终端与 JSON 输出
plugins/
  dsh/            DSH 工具与用户交互
  pi/             Pi /history 与会话交互
  cursor/         Agent 插件清单和 Skill 打包配置
skills/ai-history/  一份 Skill 源文件，不为每个宿主复制维护
```

同一个仓库、一个共享 TS 核心。先让核心和 CLI 共用根 TypeScript 包；只有宿主要求独立清单或独立发布的地方，才单独打包。DSH/Pi 的插件代码调用核心，不调用 CLI，也不负责解析历史；Cursor 通过 Skill 使用 CLI。未来的 Web 后端也可以调用核心，现在不建空目录。Go 代码在过渡期留在现有位置，不为了整理目录提前搬迁。

依赖只朝一个方向：**入口 → 核心 → readers**。reader 只知道本地存储和归一化模型，不知道自己被哪个宿主调用；核心不依赖宿主 SDK。首版不引入后台进程、索引库、依赖注入框架或通用插件注册框架。新增来源先加一个 reader，出现实际复杂度再拆。

## 2. 模型与接口

- **会话引用**：来源 + 该来源的会话 ID。UI 不拿文件路径当 ID，也不因为两个来源的标题或文本相同就合并会话。按 ID 读取仍要重新检查项目范围。
- **会话摘要与详情**：摘要只含标题、来源、项目归属、最近活动时间和可选短片段；详情按需读取。保留有意义的原生差异，例如 Pi 的活动分支，不保存所有宿主内部事件。
- **交接草稿**：包含来源引用和有长度上限的历史依据。首版可以选取相关片段，不必自动抽取一份「决策和待办」清单；不能把推测标成用户已确认的结论。核心只生成草稿，不负责发送。

核心 API 从四个操作起步，不与旧 CLI 命令逐一对应：

| 操作 | 返回或约束 |
| --- | --- |
| `inspectSources()` | 来源可用性和诊断；不读取会话正文。 |
| `querySessions({ query?, filters?, limit? })` | 在已授权的项目范围内，按时间、目录和来源筛选；有内容就按相关性排序，无内容就按最近活动浏览。返回命中位置和部分失败诊断。 |
| `openSession(ref, options?)` | 按引用读取会话；可从命中位置打开一段有长度限制的前后文。 |
| `prepareHandoff(ref, options?)` | 生成有来源、可截断的交接草稿；不发请求，也不写入当前会话。 |

创建引擎时，由入口根据可信宿主信息或用户明确选择绑定项目范围和来源配置。每个查询或读取都使用该范围，不接受模型传入的任意路径。宿主或系统负责授予读取权限；项目筛选和引擎配置不会授予权限。诊断对外展示哪些字段、CLI JSON 等细节留到正式规格，不需要现在定义完整 SDK。

## 3. 搜索契约

- **硬筛选决定候选范围。** 时间、目录、来源之间取交集；同一来源列表内任一选中来源都可命中。时间按会话最近活动时间，不是命中消息的发送时间。查询可以没有关键词，按最近活动浏览即可。结果少或为空时不自动放宽条件。
- **内容决定命中与排序。** 首版用词法搜索（lexical search），重点让多关键词、精确短语、错误码和文件名好找。结果给出会话引用、来源、活动时间、命中片段和可打开前后文的位置；「无匹配」与「有来源未搜全」分别报告。先不因选定词法搜索而要求建索引。
- **语义搜索暂不实现。** 先积累「词不同、意思相近」的漏查案例，再判断本地可选的语义模式是否有价值。无论以后用哪种内容匹配方式，都必须遵守相同的硬筛选，不自动跨项目或放宽时间。

现有 Go CLI 可用作对照：它按来源、目录筛选后逐会话扫描，做不区分大小写的连续子串匹配；没有语义搜索、时间范围或来源多选。见[搜索实现](../internal/core/search.go#L23-L73)、[文本匹配](../internal/core/search.go#L151-L180)和 [CLI 参数](../internal/cli/cli.go#L213-L226)。

## 4. 两条默认规则

**项目边界**：优先使用宿主确认的项目根；若宿主只提供当前目录，可从这个可信路径识别 Git worktree 根。非 Git 项目使用明确选定的工作目录；都无法确定时请用户选择，不默认扫描全部历史。项目根可包含下属目录，不自动合并同仓库的其他 worktree。路径用平台感知的目录关系比较，不能用字符串前缀；路径别名或 Windows/WSL 路径无法可靠对应时，不猜测归属。项目筛选不能代替读取权限：不能安全读取的来源标记为不可用。

**发送边界**：用户主动查找才能开始读取；进入对话前要明确选中会话。搜索片段和旧会话标题也可能包含隐私，不能把返回给 Agent 的结果叫作「本地预览」。

- **Pi**：优先由 `/history` 在 TUI 中预览；确认才将草稿交给当前对话，取消不发送。
- **DSH**：如果首版只有模型工具，先把它当查找入口。交接正文须在用户明确同意后才交给模型；若宿主不能可靠执行这个确认，就不开放该工具的正文输出，改用用户命令或终端预览。专用 Web 面板不是前置条件。
- **Cursor**：Skill 走 CLI，并明确说明 Agent 工具结果不是私人预览。需要先独立查看时，让用户从终端运行 CLI；不承诺 Skill 本身能提供隔离的预览界面。

## 5. 怎么判断 Agent 好不好用

**分两层测。** 先直接调核心，给定筛选条件和查询文本，检查正确会话和证据是否出现、干扰项是否被排除；再让 Agent 在正常对话中收到自然语言任务，不告诉它工具名、调用顺序或答案。前者测「工具找不找得到」，后者测「Agent 会不会选对工具、传对条件、用对结果」。

- **样例**：先做 8–12 条带标准答案的合成历史任务。包括组合筛选、只筛选不搜词、精确错误码、另一个项目或时间窗里的同词干扰、没有结果、部分来源读取失败，以及不需要查历史的请求。每条标记允许范围、预期会话和证据，或明确要求报告没有结果/部分结果。另记只记得意思的漏查案例，为后续语义搜索提供样本。
- **对照**：在同一个宿主和模型版本里，使用相同样例、当前目录、权限和任务，分别跑现有 CLI + Skill 与新版入口。每轮开新会话，关键场景重复几次。若只想比较工具名、描述或参数设计，则保持搜索引擎不变，一次只改一个地方。
- **判分**：主要看最终是否找对会话、引用了能支持答案的原文，或在无匹配时诚实说明；不要求复述固定措辞。越过目录、来源或时间限制，以及把部分结果说成完整，单独列为失败，不能被高命中率抵消。另记首个调用是否有效、调用次数和返回长度。
- **定位问题**：核心找不到 → 改筛选、匹配或数据读取；核心找得到但 Agent 没调用、选错工具或漏传条件 → 改工具名、说明或参数；候选已返回却引用错 → 改排序和输出，例如让来源、时间与命中位置更醒目。先检查调用轨迹，不急着用另一个模型打分，也不需要先建评估平台。

### 日常试用：先人工收集反馈

真实任务结束后，主动问 Agent：「刚才是怎么查历史的？哪一步让你不得不猜、重试或绕路？」由维护者记录任务意图、具体障碍和绕行方式；也收集 Agent 没发现工具、直接去翻日志的情况，这些不会出现在工具自己的记录里。没有遇到问题就不必记。

首版不做反馈入口或自动上报。等反馈难以归档、人工整理成本明显时，再考虑本地入口：Agent 起草，用户预览确认后才保存；默认不记录历史正文、原始查询或绝对路径，不自动外发。

## 6. 迁移与第一条验收路径

旧 Go 实现用于提取存储格式、兼容路径和异常样例，不规定新版命令或 JSON。优先保留已有用户真正依赖的能力；对外接口逐项选择「保持／给迁移方式／暂不迁移」，结构发生不兼容变化时不用旧 schema 名称。预览不覆盖 Go CLI；在迁移表和回退方案完成前不切默认安装入口。

设计通过后，先在 DSH **用组合条件找到当前项目里的一条 Cursor 会话并定位到命中段落**，通过搜索闭环后再用 Pi 预览同一条交接；两端不调用 Go。其他项目的会话 ID 不可打开，一个来源失效后仍应返回其余结果并注明，取消交接不发送。Node.js/SQLite/zstd 适配和发行最低版本留给后续验证，不通过提前加架构层来预判问题。
