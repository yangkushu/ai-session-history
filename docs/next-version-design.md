# 下一版设计：独立的 TypeScript 历史引擎

状态：核心设计草案，待评审。依据[下一版规划](next-version-plan.md)，本批先把核心设计完整，再统一实现。未来插件可以直接调用核心，但不在本文决定插件功能、宿主审批、公开 CLI 或发行方式。旧 Go CLI 不变。

## 1. 本批交付

- 一份独立于 Go CLI 和宿主 SDK 的 Node.js/TypeScript 核心，能发现、浏览、搜索和打开 Pi、DSH、Cursor 的会话。
- 三个 reader，共用会话模型和诊断。使用仓库合成样例做自动验收，并用一个仅供开发验收的脚本读取本机真实历史。
- 不做交接草稿生成、导出、持久化索引、语义搜索、后台服务或插件。Codex 和 Claude Code 不在本批迁移，继续使用 Go 版。不会安装或覆盖用户已有命令。

建议核心放在 `src/core/`，各来源 reader 放在 `src/core/readers/`，验收脚本放在 `scripts/`。依赖方向是调用者 → 核心 → reader：核心决定筛选、排序和诊断，reader 决定存储发现、格式解析及归一化。首批以实测过的 Node 24 为开发与验收基线，不据此宣布发行最低版本。

## 2. 核心契约

| 操作 | 返回或约束 |
| --- | --- |
| `inspectSources()` | 返回已配置来源的可用性和诊断；只探测发现路径、可访问性及所需运行时能力，不读取会话正文。 |
| `querySessions({ query?, filters?, limit?, signal? })` | 有词时搜索，无词时浏览。返回有限的会话摘要、命中证据和查询完整性。筛选包含可选的 `under`、活动时间范围和来源列表。 |
| `openSession(ref, { anchor?, limit?, signal? })` | 按来源和原生 ID 打开长度受限的可见内容；有 `anchor` 时打开命中及有限前后文。不会继承前一查询的筛选条件。 |

- **标识与摘要**：`ref` 由来源和原生会话 ID 组成，不用文件路径当 ID，不合并不同来源的同名会话。摘要含引用、显示标题、可用的会话目录和最近活动时间。活动时间优先用来源记录的更新时间、再用创建时间；时间未知时不猜测。
- **正文**：首批搜索标题和用户/助手的可见文本。展示正文使用同一批可见文本，不读取内部思考、系统提示、工具参数、附件二进制或扩展私有数据作为搜索输入或结果。Pi 只展示活动分支；内部事件不强制逐项归一化。
- **命中位置**：结果返回短片段与不透明 `anchor`，区分标题和消息命中。消息锚点优先用原生消息 ID；没有 ID 时，用归一化消息位置及内容校验标记。打开时复核命中文本，活动分支切换或内容改变导致无法定位时，报告命中已失效，提示重搜，不误开另一段。
- **配置与权限**：来源配置决定去哪找历史；`under` 只匹配会话的目录元数据，不是文件访问路径或授权规则。核心不发现 Git 项目、不隐式读取当前工作区，也不绕过操作系统权限。

## 3. 查询行为

1. **先筛选。** 来源列表内部取并集，与时间、目录条件取交集。时间按会话最近活动时间，采用起点包含、终点不包含；有时间条件时排除未知活动时间。首版只有可选的 `under`：匹配指定目录本身及其子目录。不传就不按目录筛选；传了就按路径组成比较，不用字符串前缀，不猜测无法可靠比较的路径别名、Windows/WSL 别名或缺失的目录。见 [#1](https://github.com/yangkushu/ai-session-history/issues/1)。
2. **再匹配。** 首批建议用不区分大小写的词法匹配：空白分隔的词都要命中，但可以出现在同一会话的不同消息；双引号内的短语必须在同一标题或消息内连续出现。文件名和错误码里的标点不拆开。空关键词按活动时间浏览；无结果时不删条件重查。
3. **最后排序与限量。** 搜索结果优先匹配集中在标题或同一消息里的会话，再按最近活动时间和来源加原生 ID 作稳定排序；未知时间排在已知时间后。默认限制结果数、片段和打开的上下文长度。正常的结果截取不是来源失败；如果中止扫描或读不到候选会话，不能把结果说成完整。

不预先加载全部历史。reader 能从摘要筛掉不合格会话时先筛；必须扫描正文才能确定元数据的格式则流式解析。引擎定期检查取消信号，不发起网络请求、不自动输出正文日志。结果明确区分：完整搜索但无匹配、有来源或会话读取失败的部分结果、所有选中来源均不可用；用户主动取消单独报告。

## 4. Reader 与运行边界

| 来源 | 本批格式与规则 |
| --- | --- |
| Pi | 读取 v1–v3 JSONL，v2/v3 按活动分支回溯。沿用[已知的存储发现顺序](source-support.md#pi)，排除 `subagent-artifacts/`，损坏或未知格式单独诊断。 |
| DSH | 读取已知 v4 的 zstd JSONL；按[已知路径](source-support.md#deepseek-harness-dsh)发现，使用 Node 内置流式解压。未知版本或损坏归到该会话，不能默默跳过。 |
| Cursor | 覆盖已观察的 Windows `composerHeaders`/bubble 和 macOS `composerData` 形态。使用 `node:sqlite` 查询，不解密私有负载。真实数据和合成 fixture 分开验收；Windows/WSL 和 macOS 的路径发现、存储形态可分别标记为已验证或未验证。 |

**Cursor 活动库是当前需要拍板的读取边界。** 本机合成 WAL 实验证实：直接用 `readOnly: true` 打开活动原库时，主库虽然按只读打开，`-wal` 和 `-shm` 仍以可写方式打开，并观察到 `-shm` 内容变化。优先保障不改写源文件；建议本批使用已知一致的私有快照（可包含对应的 WAL），只在临时目录让 SQLite 建立协调文件。在合成库源端暂停写入后复制主库与 WAL，实测能读到只在 WAL 中的已提交记录，源文件名和哈希均未改变。

不能把边写边逐文件复制当作一致快照，也不能对活动原库使用 `immutable=1` 来掩盖问题。如果接受快照作为本批运行边界，真实验收可用 Cursor 已退出后的数据或由可靠方法取得的一致快照；正在更新的原库不能安全读取时，明确报告该来源不可用或降级，仍返回 Pi/DSH 结果。若本批必须直接读取正在运行的 Cursor 原库，就应先确定允许的 SQLite 协调文件行为，或另证可靠的无写入快照机制。依据见[运行时查证](next-version-host-feasibility.md)。

## 5. 验收与开工条件

| 层次 | 可验证标准 |
| --- | --- |
| 核心契约 | 合成会话验证组合条件、时间边界、词与短语、稳定排序、命中打开、过期锚点、限量、取消和部分失败。目录样例：`/work/app`、`/work/app/src`、`/work/app-old`、未知四条记录，传 `/work/app` 只命中前两条，不传四条均可命中；空结果不自动放宽。 |
| 真实 reader + 合成存储 | 通过同一个核心 API 跑 Pi、DSH、Cursor fixture。验证 Pi 只读活动分支、DSH 能流式解码且坏文件可隔离、Cursor 能读一致快照中仅在 WAL 的已提交记录且源文件无变化。加入一种来源失败而其他来源可用的组合用例。 |
| 本机真实历史 | 开发验收脚本只做参数转发和有限结果打印。Pi、DSH、Cursor 各选一条已知会话，用同一个 TS 核心搜索，根据返回的引用和命中位置打开段落；不依赖 Go CLI、不加载插件、不把真实路径和正文提交到仓库。没有数据或平台时列出未验证项，不视为通过。 |

如采纳快照边界，核心整体评审确认本文的模型、查询语义和验收标准后，再统一开工；如果不采纳，先解决活动 Cursor 库读法。已建的 #1 记录目录需求，不先于整体评审实施。插件运行时、宿主预览与 CLI 发行不再是本批开工条件。
