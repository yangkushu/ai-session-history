# `ai-history` 下一版本规划：重新设计历史引擎与三端交接

状态：**本批范围已确认：先重构核心，不做插件**。三端交接仍是后续产品方向，不是本批完成条件。核心接口和验收见[核心设计草案](next-version-design.md)。

## 1. 用户要解决什么

在同一个项目里交替使用 Cursor、DeepSeek Harness（DSH）和 Pi 时，不必记得上一段工作发生在哪个工具里。**核心功能是跨工具的多条件搜索**：按时间、目录和来源缩小范围，用内容找到那段对话，再打开命中处核对前后文。不记得关键词时，也可以只用筛选条件浏览。复制片段或生成交接是找到之后的下一步，不是首版搜索的前置条件；交接不导入、恢复或改写原宿主会话。

**这是一次重新设计，不是把 Go CLI 翻译成 TypeScript。** 从「在另一个工具里如何找回并继续工作」出发定义新模型和接口，而不是把旧命令改写成同名函数。旧实现可用于理解存储格式、平台差异、历史缺陷和用户已有的操作习惯；哪些旧行为应当延续，要按价值和迁移成本单独判断。

当前仓库已能读取 Codex、Claude Code、Cursor、Pi 和 DSH 的本地历史；[变更日志](../CHANGELOG.md#unreleased)仍将 DSH reader 标记为未发布。现有 Skill 安装目标是 Codex、Claude Code 和 Cursor。下一版的价值是新的跨宿主使用流程，不是重复添加 reader。

## 2. 从使用流程设计核心

| 能力 | 新版要先回答的问题 |
| --- | --- |
| **按目录筛选** | 核心提供可选目录过滤，由调用方（例如 Agent）决定传哪个目录。省略时不按目录筛选，在所有可读取的已配置来源中查询；核心不推断项目根、当前目录或 Git worktree。目录条件只筛选会话，不授予读取权限。 |
| **发现会话** | 没有关键词时如何列最近活动？带关键词时如何让人判断哪条是对的？以来源、时间、标题和短片段为基本线索；重新设计筛选和排序，不锁定旧评分规则。区分「没有结果」与「只查到部分来源」。 |
| **阅读会话** | 先定义能被 CLI、插件和 Web 共用的领域模型：来源、会话引用、可用的会话目录、活动时间和可展示内容。保留各宿主有意义的差异，例如 Pi 的活动分支；不强求所有事件无损映射成一种格式。 |
| **本批止于原文核对** | 核心返回命中片段和可定位的原文；生成交接草稿、预览及发送暂不设计或实现。 |

**底层：共享 TypeScript 历史引擎。** 在 Node.js 中运行，内部把来源发现、格式读取和跨来源查询/交接分开。读各家格式的 reader 不负责用户交互；查询和交接复用统一的会话模型。引擎不依赖宿主 SDK、CLI 参数或网页，不启动模型，也不发网络请求。不预设必须拆分成多个发布包。

**上层：使用入口。** CLI、插件、未来的本地 Web 后端按各自的方式调用引擎。CLI 负责命令参数和输出；插件负责宿主交互，并可向 Agent 提供工作区信息供其决定是否按目录过滤；浏览器不直接读取历史文件。CLI 是一个入口，不再作为 DSH/Pi 插件的运行时依赖。

## 3. 本批交付与后续接入

本批交付共享 TypeScript 核心、Pi/DSH/Cursor readers、自动测试和薄验收脚本。脚本只负责转发参数和显示结果，不是公开 CLI。Codex 和 Claude Code 不在本批迁移，继续用现有 Go CLI。

三端具体功能、交接界面、安装方式及新版公开 CLI 均后置。核心保持宿主无关，后续入口可以直接调用，不需要重写搜索和 reader。已查证的宿主能力和风险保留在[宿主与运行时查证](next-version-host-feasibility.md)，不作为本批开工门槛。

**搜索首版：** 时间按会话最近活动时间；目录只支持可选的 `under` 筛选，匹配指定目录及其子目录，不传就不按目录筛选；来源可多选。硬条件之间取交集，不因结果少而自动放宽。内容用词法搜索，重点支持多关键词、精确短语、错误码和文件名，结果能定位到原文。

**本期不做：** 语义搜索、MCP、独立 Web 页面、常驻服务、持久化索引、云同步、自动导入或回填会话。语义搜索待根据「记得意思但记不得原话」的实际漏查案例决定，若加入，优先考虑本地可选模式，不改变硬筛选。本批不做交接草稿或完整导出；新版 CLI 如何提供这些能力，留到后续接入设计。

**试用反馈：** 先由维护者在真实任务后主动询问 Agent、人工整理反馈。首版不开发反馈入口、不自动收集；等反馈容易散失或重复整理的成本明显时，再考虑增加本地入口。

## 4. 旧版怎么用，哪些不能丢

| 类别 | 处理方式 |
| --- | --- |
| **产品承诺** | 保留本地优先、源存储只读、权限不可绕过、默认不自动发送历史。历史文本视为不可信资料；工具结果可能被宿主发给远端模型。来源权限不足、单文件损坏或格式不支持时，不影响其他来源给出结果，默认不记录历史正文。 |
| **参考材料** | 从旧 Go readers、[来源说明](source-support.md)、合成样例和既有测试提取格式、路径发现和异常案例。特别关注 Cursor 活跃 SQLite/WAL、DSH zstd、Pi 活动分支、Windows/WSL 与自定义历史目录。不以逐字段输出一致代替新版验收。 |
| **允许重做的接口** | 内部数据模型、reader 和查询 API、配置组织、搜索排序、交接内容，以及 CLI 命令和 JSON 契约都可重新设计。明确哪些需要延续，例如已被脚本或 Skill 使用的参数、来源限定 ID、导出或交接 schema；不承诺全部原样保留。 |
| **对用户的迁移** | 发布前按 [现有 CLI 规范](../openspec/specs/cli/spec.md)、[导出规范](../openspec/specs/session-export/spec.md)和[安装指南](installation.md)列出「直接兼容／有替代方式／本期不迁移」。语义不兼容时不要沿用旧 schema 版本；按影响选择兼容适配、迁移示例或旧版并行。预览不覆盖已安装的 Go CLI，不让用户在不知情时突然需要 Node.js。 |
| **运行与响应性** | 避免插件加载时扫描，不把全部历史一次读进内存。查询应可取消、有结果和输出上限。后续再决定 Node 内置 SQLite/zstd 能否满足宿主与平台矩阵，以及是否需要 worker 或进程内缓存。 |

## 5. 后续顺序与发布门槛

按[项目开发约定](../AGENTS.md)，Agent 用自己的设计流程起草简短设计，GitHub Issue 跟踪可独立验收的改动及验收条件，不绑定特定 spec 工具。既有规格保留作兼容性和历史参考。

1. **先完成核心整体设计并评审。** 确认会话模型、搜索、三种 reader、Cursor 安全读取边界和验收标准。[#1 `under` 目录筛选](https://github.com/yangkushu/ai-session-history/issues/1)只是已确认的需求记录，不先于整体设计实现。
2. **统一实现并独立验收核心。** 不用宿主插件或 Go CLI，从 Pi、DSH、Cursor 都能找到已知会话并定位原文。用自动测试验证行为，用本地真实历史查证发现和读取；缺少环境时记录未验证项。
3. **后续再设计产品入口。** 核心验收后，再评审三端接入及新版公开 CLI、兼容性和发布；本批不替换默认 CLI。

当前仍在核心设计阶段。剩余决策和验收细则见[核心设计草案](next-version-design.md)。
