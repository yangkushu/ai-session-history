# `ai-history` 下一版本规划：重新设计历史引擎与三端交接

状态：**草案，待确认**。本文定义产品目标、设计边界和发布策略，不锁定 API、运行时版本或发布版本号。代码结构和核心接口建议见[下一版设计草案](next-version-design.md)。

## 1. 用户要解决什么

在同一个项目里交替使用 Cursor、DeepSeek Harness（DSH）和 Pi 时，不必记得上一段工作发生在哪个工具里。**核心功能是跨工具的多条件搜索**：按时间、目录和来源缩小范围，用内容找到那段对话，再打开命中处核对前后文。不记得关键词时，也可以只用筛选条件浏览。复制片段或生成交接是找到之后的下一步，不是首版搜索的前置条件；交接不导入、恢复或改写原宿主会话。

**这是一次重新设计，不是把 Go CLI 翻译成 TypeScript。** 从「在另一个工具里如何找回并继续工作」出发定义新模型和接口，而不是把旧命令改写成同名函数。旧实现可用于理解存储格式、平台差异、历史缺陷和用户已有的操作习惯；哪些旧行为应当延续，要按价值和迁移成本单独判断。

当前仓库已能读取 Codex、Claude Code、Cursor、Pi 和 DSH 的本地历史；[变更日志](../CHANGELOG.md#unreleased)仍将 DSH reader 标记为未发布。现有 Skill 安装目标是 Codex、Claude Code 和 Cursor。下一版的价值是新的跨宿主使用流程，不是重复添加 reader。

## 2. 从使用流程设计核心

| 能力 | 新版要先回答的问题 |
| --- | --- |
| **定位项目** | 宿主能提供什么项目身份？项目根、子目录、Git worktree 如何关联？建议同一项目根下的子目录可一起搜索，不默认跨 worktree；判断不了就让用户选择，不扩大为全局搜索。按会话 ID 打开或交接时重用同一个范围约束。 |
| **发现会话** | 没有关键词时如何列最近活动？带关键词时如何让人判断哪条是对的？以来源、时间、标题和短片段为基本线索；重新设计筛选和排序，不锁定旧评分规则。区分「没有结果」与「只查到部分来源」。 |
| **阅读会话** | 先定义能被 CLI、插件和 Web 共用的领域模型：来源、会话引用、项目归属、活动时间和可展示内容。保留各宿主有意义的差异，例如 Pi 的活动分支；不强求所有事件无损映射成一种格式。 |
| **预览与交接** | 区分原始会话、搜索片段和交接草稿。交接有来源、有长度上限，不把历史中的猜测当成已确认决策。核心只生成草稿，是否以及如何发送由宿主和用户决定，不自动恢复原会话。 |

**底层：共享 TypeScript 历史引擎。** 在 Node.js 中运行，内部把来源发现、格式读取和跨来源查询/交接分开。读各家格式的 reader 不负责用户交互；查询和交接复用统一的会话模型。引擎不依赖宿主 SDK、CLI 参数或网页，不启动模型，也不发网络请求。不预设必须拆分成多个发布包。

**上层：使用入口。** CLI、插件、未来的本地 Web 后端按各自的方式调用引擎。CLI 负责命令参数和输出；插件负责使用宿主的项目与交互能力；浏览器不直接读取历史文件。CLI 是一个入口，不再作为 DSH/Pi 插件的运行时依赖。

## 3. 三端交付与分发

| 入口 | 首版交付草案 |
| --- | --- |
| **DSH** | 原生插件提供项目内搜索和选中会话后的交接。若用 Agent 工具，说明结果会进入模型上下文；如果要求确认前只能由用户预览，就需要用户命令或界面，而不只是 Agent 工具。先不承诺专用 Web 面板。 |
| **Pi** | Extension 提供 `/history`：搜索、选中、预览，再由用户确认带入对话。 |
| **Cursor** | Agent 插件以[现有 Skill](../skills/ai-history/SKILL.md)为起点，通过 CLI 使用新核心；按新版流程调整 Skill，不把旧 Skill 的调用方式强加给引擎。不做编辑器扩展。 |

DSH/Pi 直接引用共享引擎，目标是使用同一份 JS 产物，不内置、不下载，也不要求预装 Go binary；尽量不依赖按平台发布的 npm 原生扩展。独立 TS CLI 和 Cursor 的 Skill 路径仍需要兼容的 Node.js。需分别记录 DSH Desktop/CLI、Pi 和独立 CLI 的最低运行时版本，不能假定 Cursor 终端一定有兼容的 Node.js。

**搜索首版：** 时间按会话最近活动时间；目录默认当前项目；来源可多选。硬条件之间取交集，不因结果少而自动放宽。内容用词法搜索，重点支持多关键词、精确短语、错误码和文件名，结果能定位到原文。

**本期不做：** 语义搜索、MCP、独立 Web 页面、常驻服务、持久化索引、云同步、自动导入或回填会话。语义搜索待根据「记得意思但记不得原话」的实际漏查案例决定，若加入，优先考虑本地可选模式，不改变硬筛选。完整导出不列为首版插件功能；新版 CLI 如何提供导出，纳入兼容与迁移评审。

**试用反馈：** 先由维护者在真实任务后主动询问 Agent、人工整理反馈。首版不开发反馈入口、不自动收集；等反馈容易散失或重复整理的成本明显时，再考虑增加本地入口。

## 4. 旧版怎么用，哪些不能丢

| 类别 | 处理方式 |
| --- | --- |
| **产品承诺** | 保留本地优先、源存储只读、权限不可绕过、默认不自动发送历史。历史文本视为不可信资料；工具结果可能被宿主发给远端模型。来源权限不足、单文件损坏或格式不支持时，不影响其他来源给出结果，默认不记录历史正文。 |
| **参考材料** | 从旧 Go readers、[来源说明](source-support.md)、合成样例和既有测试提取格式、路径发现和异常案例。特别关注 Cursor 活跃 SQLite/WAL、DSH zstd、Pi 活动分支、Windows/WSL 与自定义历史目录。不以逐字段输出一致代替新版验收。 |
| **允许重做的接口** | 内部数据模型、reader 和查询 API、配置组织、搜索排序、交接内容，以及 CLI 命令和 JSON 契约都可重新设计。明确哪些需要延续，例如已被脚本或 Skill 使用的参数、来源限定 ID、导出或交接 schema；不承诺全部原样保留。 |
| **对用户的迁移** | 发布前按 [现有 CLI 规范](../openspec/specs/cli/spec.md)、[导出规范](../openspec/specs/session-export/spec.md)和[安装指南](installation.md)列出「直接兼容／有替代方式／本期不迁移」。语义不兼容时不要沿用旧 schema 版本；按影响选择兼容适配、迁移示例或旧版并行。预览不覆盖已安装的 Go CLI，不让用户在不知情时突然需要 Node.js。 |
| **运行与响应性** | 避免插件加载时扫描，不把全部历史一次读进内存。查询应可取消、有结果和输出上限。后续再决定 Node 内置 SQLite/zstd 能否满足宿主与平台矩阵，以及是否需要 worker 或进程内缓存。 |

## 5. 后续顺序与发布门槛

1. **先定搜索契约和验收用例。** 写清楚会话模型、硬筛选与内容匹配、命中定位、宿主的数据可见性和兼容矩阵。不以复刻旧 CLI 作为任务分解。
2. **跑通最小搜索闭环。** DSH 能按条件找到当前项目的一条 Cursor 会话，并定位到命中段落；用有标准答案的场景分别检查核心搜索和 Agent 是否会用。再把同一条命中结果接到 Pi 的预览，两端不调用 Go。另看 DSH zstd 是否能在目标运行时读取。如果宿主权限或跨平台要求无法满足，回到设计取舍，而不是静默放宽权限或改成平台专用包。
3. **发布三端预览。** 验收以找对会话、核对原文为先，再跑「Cursor 留下决策和待办 → DSH 找回并继续 → Pi 找回 DSH 的进展并预览交接」。覆盖项目边界、部分来源失败、权限拒绝和用户取消。Codex 和 Claude Code 作为已有来源，不在预览阶段静默移除；即使尚未迁入 TS，也继续可通过旧 CLI 使用。
4. **单独决策是否替换默认 CLI。** 根据新版产品验收、已承诺的来源覆盖、公开迁移说明和可执行的回退方案决定。旧 Go 版在过渡期是可用回退和参考实现，不是需要长期同步开发的第二套引擎。

待优先拍板：**项目根如何确定**、**DSH 是否必须在模型看到正文前提供纯本地预览**、**哪些旧 CLI/JSON 接口值得做兼容**。本轮仅更新规划，不启动验证或实施。
